# 产品决策记录

本文件记录已拍板的方向与边界。与讨论稿（`PRODUCT_NOTES.md`）的区别是：这里的内容是结论，改动需要明确推翻。

## North Star

**让浏览器从「按页面组织」变成「按正在做的事情组织」。**

> Context Workspace 是一个以「任务上下文」为核心的浏览器工作区工具。它帮助用户将同一件事相关的网页与状态组织为独立 Context，并支持快速保存、关闭、恢复和切换工作现场，从而降低多任务环境下的上下文切换成本、标签混杂和意外暴露。

四层目标：

1. Context 是浏览器里的「任务单位」，与 Tab / Window / History / Bookmark 并列。
2. Context 能被「进入」和「退出」：进入即恢复工作现场，退出即收起工作现场。
3. 不同 Context 之间减少相互干扰，包含认知负担与视觉暴露两个方面。
4. Context 具备「连续性」，用户能知道上次做到哪了。当前仅靠手写 `note`，不引入第二套进度数据。

三个「不做」：不做万能浏览器、不做安全 / 隐私容器、不做某个垂直场景专用工具。秋招只是第一个验证场景。

**功能过滤器**：任何新功能先回答「它有没有让进入、退出、恢复、切换一个 Context 更容易？」没有就不做。唯一例外是明确标注「研究脚手架、用完即拆」的临时设施。

## 威胁模型

防**意外暴露**：第三方瞄到屏幕造成的尴尬。
不防**对抗性访问**：有人存心翻电脑不在解决范围内。

由此推出：不做加密、不做密码锁、不承诺任何隐私保护。

硬约束：Chrome 不提供扩展级会话容器 API，Firefox 的 Multi-Account Containers 在 Chrome 没有等价物。扩展无法隔离 cookie、登录态或浏览历史，真隔离只能依靠 Chrome Profile。对外话术只说「视觉与组织上的分开」。

## 0.2 决策

### D1 窗口内新开标签的归属

采用「窗口承载现场，Context 保存确认快照」。用户在 Context 窗口里手动新开的标签处于待保存状态，不自动写入 Context；Restore 只恢复已保存资源；Close 时列出本窗口未保存的新标签供勾选，勾选的先保存再关闭，未勾选的保留并在结果中说明。

**红线：只有确实存在未保存新标签时才显示确认列表。没有新标签时 Close 必须保持一键完成。** 无条件在退出路径上加审阅会让退出变难，违反功能过滤器。

### D2 窗口识别

Chrome 窗口没有名称，`chrome.windows` 也不提供命名接口。0.2 只实现侧边栏显示当前窗口关联的 Context 名称。手动命名窗口引导、工具栏徽标、标识标签页等候选记录但不实现。

### D3 浏览器重启后窗口映射丢失

窗口↔Context 映射存在 `chrome.storage.session`，重启即清空，行为退回 0.1 语义。**不尝试用 URL 重新认领窗口**，与既有「不凭 URL 猜测归属」边界一致。

### D4 Local Usage Events 的定性

这不是产品功能，是**研究脚手架，用完即拆**。用户研究结束后应整体移除 `src/storage/usage.ts` 及其调用点。导出前用户必须能看到完整内容并自行删改，不得静默导出；事件写入失败只能吞掉，绝不允许影响主流程。

### 本轮明确砍掉

Archived 生命周期管理（过期提醒、坟场效应防治）推后。道理成立，但当前 Context 数量少，痛感未出现，先在数据模型上留位置即可。

### D5 Discreet 不影响搜索

**Discreet 只管静态展示，不管用户主动搜索。** 按资源标题搜索对 discreet Context 依然有效。

理由：被动展示与主动搜索在威胁模型上性质不同。列表静置时被旁人瞄到属于意外暴露，而搜索是用户自己发起的。搜索结果仍然只渲染 Context 名称（`ContextList` 在 discreet 时只显示名称，`ContextDetail` 不展示资源区），旁人看到的是「秋招」而非「京东 - 产品经理」，没有新增暴露面。至于他人主动输入关键词探测某个 Context 的内容，那属于对抗性访问，本就不在威胁模型内。

产品理由同样决定性：秋招场景的核心就是按公司名找到对应 Context。搜不到京东、美团、快手，这个场景直接失去意义。

## 待裁决

**「一键切换」与「宁少关不误关」的冲突。** 切换 = 退出当前 + 进入目标，但保守关闭策略意味着退出时可能关不干净，切换到一半留着上一个 Context 的标签，体验是坏的。0.2 的处理是如实告知（结果消息中报告其他窗口的遗留标签数），但没有真正解决。

### 候选方案：用户可调的「保守程度」高 / 低

已评估，**不实现**。结论记录在此，避免以后重新辩一遍。

「保守」不是一个程度，而是四件事捆在一起。`closeContext` 跳过标签只有四种情况：标签已关闭或 URL 已跳转、被另一个 Context 共享、关闭前二次校验撞上并发导航、标签在其他窗口。前三类放宽等于接受误关他人页面，而且不可撤销——只恢复 URL 不恢复表单输入，误关即丢失。**一个开关若有一档的含义是「接受误伤」，这一档就不该存在**，它不是给用户的自由，是把设计难题外包给用户。

与状态标签的类比不成立：状态是描述性的，描述这件事现在怎么样了，填错没有代价；保守程度是行为性的，预先决定一个破坏性操作如何执行。时机也不对——用户在创建 Context 时并不知道将来退出会不会遇到共享标签、跳转或未保存输入，这是在信息最少的时刻对未来做承诺。

**真正可调的只有「是否跨窗口关闭本 Context 的标签」这一维**，且不需要开关：把结果消息里的「另有 N 个……未关闭」变成可点击的后置动作即可，决定推迟到残留已经发生、数量已知的时刻。此方案同样推后，先验证痛点是否真实存在。

**研究观察点**：用户切换后遇到残留标签时，是手动关掉、直接无视，还是回过头来找功能？这个行为差异决定要不要做，以及做成后置动作还是别的形态。

## 下一步

0.2 完成后**停止写代码**，找 5 位真实用户使用**至少一周**（不是 2–3 天，少于一周只能测到新鲜感，测不到习惯）。

用户筛选按行为而非身份：找对混乱感到痛苦、且已经在用土办法对付它的人（自建表格记链接、拿书签栏当暂存区、专门开另一个 Profile）。筛选问题用「你上次因为标签太乱找不到东西是什么时候，当时怎么办的」，而不是「你平时开几个标签」。

研究方法上，行为日志在 5 人样本下**不做统计推断**，而是用于**事实对质**：用户说「我每天都在用」而日志显示只恢复过一次，这种说与做的差异才是小样本里最有价值的信息。因此需要的是每个用户的时间线，不是聚合比例。
