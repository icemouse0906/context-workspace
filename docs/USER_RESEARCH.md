# 0.2 用户研究执行手册

目标：回答一个问题——**Context 能不能成为一种真实存在的「任务切换单位」，还是只是作者本人的偏好。**

规模：5 人，每人**至少一周**。少于一周只能测到新鲜感，测不到习惯。时间不够宁可少找两个人，不要缩短周期。

## 一、招募与筛选

### 按行为筛，不按身份

不要找「标签页特别多的人」。开着 100 个标签还活得很好的人，对混乱的容忍度本来就高，他们不是你的用户。

要找的是**对混乱感到痛苦、并且已经在用土办法对付它的人**。土办法的存在是痛点真实的唯一证据。

### 筛选问题（按顺序问，不解释目的）

1. 「你最近一次因为标签太多、找不到之前看过的页面，是什么时候？」
   —— 想不起来的，不合格。

2. 「那次你是怎么处理的？」
   —— 听是否出现土办法：建表格记链接、拿书签栏当临时暂存、发给自己微信、开新的 Chrome 配置、截图存下来。**有土办法的优先。**

3. 「现在你手上同时在推进几件需要用浏览器的事？」
   —— 少于 2 件的不合格，他没有切换需求。

4. 「这些事里，有没有哪件你今天不做、过两天还得接着做？」
   —— 全是一次性任务的不合格，测不到「恢复」。

### 目标构成

秋招 2 人（和你自己的场景对照），另外 3 人来自长周期、反复回访的场景——写作、备考、做调研课题、推进某个项目。至少要有 1 个长周期用户，否则「恢复」这个核心动作可能根本不会被触发。

### 不要找的人

同学、室友、关系很近的朋友。他们会为了不让你难堪而假装在用。宁可找弱关系。

## 二、知情同意（第一次见面开头念）

> 「这个工具所有数据只存在你自己电脑的浏览器里，不上传，我看不到你的网址和网页内容。它也会在本地记一份很简单的操作记录——只有『你创建了一个任务』『你恢复了一个任务』这种动作和时间，不含任何网址或标题。一周后我想请你把这份记录导出给我，导出前你能完整看到内容，不想给的部分可以自己删掉。全程你随时可以说不。可以吗？」

对方同意后再继续。访谈过程如果要录音，单独再问一次。

## 三、第一次见面（约 60 分钟）

### 第 1 段：先看现状，不提产品（20 分钟）

**全程不要说出「Context」这个词，不要介绍你做了什么。**

- 「能不能打开你现在的浏览器，让我看看？」——看标签数量、有没有分组、书签栏长什么样。
- 「这些标签里，哪些是同一件事的？」——**听他怎么划分，这是粒度问题的第一手答案。**
- 「你昨天/上周做的那件事，现在还能找回来吗？做给我看。」——**观察他找回的真实过程和耗时，这是你的基线。**
- 「这里面有没有你不敢关的？为什么？」

记录：他自发使用的分组词汇是什么（项目？事情？任务？还是直接说公司名）。后面介绍产品时**用他的词**，不要用你的。

### 第 2 段：安装与首次使用（25 分钟）

装好后只说一句：「你可以把同一件事相关的页面存成一组，之后一次性关掉和打开。」然后闭嘴。

**不要演示，不要解释按钮。让他自己摸。**

要观察并记下的：
- 他第一个建的是什么，**他给它起了什么名字**——这是粒度问题的核心数据（一个岗位？整个秋招？今天晚上？）
- 他建了几个
- 他是逐个「添加当前标签页」，还是找到了「保存当前窗口」
- 确认列表出现时，他有没有真的去取消某几个，还是直接全部确认
- 他有没有填备注、分类、状态；填了什么
- 第一次卡住是在哪一步，卡了多久
- 他有没有问「这个会不会上传」之类的问题

**他卡住的时候不要救他**，等 30 秒。看他自己怎么解。

### 第 3 段：关闭与恢复（15 分钟）

请他保存一组页面之后把它们关掉，然后恢复。

- 恢复到新窗口的那一刻，他的第一反应是什么
- 问：「现在这个窗口对你来说是什么？」——**检验「窗口 = 任务」这个心智成不成立**
- 他能不能分辨哪个窗口是哪个任务
- 如果窗口里有没保存的新标签，「关闭 Context 窗口」的确认列表弹出来时他怎么反应：是觉得贴心，还是觉得烦

最后说：「接下来一周你正常用就行，不用刻意。有问题随时找我，但我不会主动打扰你。」

## 四、第 2 天（最关键的一次，15 分钟，可以微信语音）

**这是整个研究里信号最强的一次接触。** 核心只有一个问题：

> 「昨天存的那些，今天打开了吗？」

- **打开了**：问「是怎么想起来要打开的？当时在做什么？」——找出触发点，这是形成习惯的关键。
- **没打开**：问「今天那件事你做了吗？」
  - 做了但没用 → **这是最重要的信号。** 问「那你是怎么找回那些页面的？」说明工具没进入他的路径。
  - 根本没做 → 不算负面信号，继续观察。

不要在这一天问「好不好用」。只问他做了什么。

## 五、一周中间（第 4 天左右，微信文字即可）

一句话：「这两天还在用吗？」

不要追问。回答是什么就是什么，沉默和敷衍也是数据。

## 六、第 7 天结束访谈（约 45 分钟）

### 先要日志，再问问题（顺序很重要）

让他导出行为记录，当面确认内容后发给你。**先拿到日志再开始问**，否则你会被他的叙述带偏。

### 核心对质环节

把日志摊开，逐条对。这是小样本研究里最值钱的部分：

- 他说「一直在用」，日志显示只恢复过 1 次 → **问这个差异**，不要戳穿，问「我看记录里恢复的次数不多，是不是有些时候用了别的方式？」
- 日志里存了但从没恢复过的 Context → 「这几个后来怎么样了？」
- 创建后两天内就没动过的 → 「当时建它是想干嘛？」

**说的和做的不一致，是你能拿到的最有价值的发现。** 不要试图让他们一致。

### 要回答的问题清单

粒度与命名
- 他最终形成的 Context 是什么粒度？和第一天建的第一个相比变了吗？
- 有没有出现他自己中途改名或者合并/拆分的情况？

进入与退出
- 「保存后放心关掉」真的发生了吗，还是他其实不敢关？
- 恢复只打开 URL，够不够找回现场？缺的是什么？（滚动位置、输入内容、登录态、页面顺序）
- 备注写了吗？第二次回来会读吗？还是直接看页面？

0.2 新功能
- 「保存当前窗口」的确认列表：帮助还是摩擦？有没有人真的取消过某几项？
- 「关闭 Context 窗口」的确认列表（有未保存新标签时）：理解吗？会不会觉得「怎么又要我选」？
- 一个 Context 一个窗口：这个心智成立吗？窗口多了之后会不会反而乱？
- 他能认出哪个窗口是哪个 Context 吗？用的什么办法？

边界理解
- 页面跳转后失去关联、重启后旧标签不被认领——他遇到过吗？怎么理解的？生气吗？
- 保守关闭（宁少关不误关）造成的「没关干净」，他注意到了吗？

Discreet（**不要直接问**）
- 看设置里有没有被开启过。如果开过，中性地问「这个只显示名称的开关你什么时候会用？」
- **不要追问他用它装了什么。** 追问会让人撒谎，也破坏信任。他开过这件事本身就是数据。

状态与分类
- `category` 和 `status` 这两个字段，他填了吗？一周下来改过吗？
- 如果一次都没碰过，这两个字段就该考虑砍掉。

对照现有工具
- 「这一周里，有没有哪次你没用它、而是用了以前的办法？」
- 「如果明天这个工具没了，你会难受吗？还是回到以前就行？」——**这题的答案基本决定产品有没有继续的必要。**

## 七、怎么看数据（重要）

**5 个人一周的数据不做统计推断。** 任何「百分之多少」都是噪音——60% 可能就是 3 个人里的 2 个。不要在任何地方写「数据表明」。

日志的唯一用途是**事实对质**：给访谈提供具体锚点，让你能指着某一天问「这天发生了什么」。所以你要的是每个人的时间线，不是聚合比例。

**最该关注的单一信号**：第 2 天之后，有没有人在你没提醒的情况下自己点了恢复。有，产品有戏；全员没有，「降低任务切换成本」这个命题就没被验证，再多功能也救不回来。

## 八、你自己要克制的三件事

1. **不要解释。** 用户说「我没搞懂这个按钮」时，你想解释的冲动就是产品失败的证据。记下来，别救场。
2. **不要辩护。** 「其实你可以这样……」这句话一出口，这次访谈的数据就废了。
3. **不要诱导。** 不问「你觉得这个功能有用吗」（所有人都会说有用），只问「你上次用它是什么时候，当时在干嘛」。

## 九、一周后的输出

做完 5 个人，写一份不超过两页的东西，包含：

- 5 个人各自的 Context 命名列表（原文照抄，不要归纳）——粒度问题的答案在这里
- 第 2 天回访率：几个人自发恢复了
- 说与做不一致的具体案例
- 每个「仍未验证的问题」现在的状态：被支持 / 被推翻 / 仍未知
- 一句话结论：这是作者的偏好，还是一种真实存在的工作方式

然后再决定要不要写 PRD、做 Figma、进入下一轮开发。
