# 产品讨论笔记 · 第一版

## 当前产品命题

「任务」可能是比网页、标签或网站更贴近用户意图的组织单位。一个 Context 保存一组相关网页和用户手写进度，通过关闭与恢复支持任务切换。现在只是待验证的产品命题，不是已经成立的结论。

首轮以秋招多岗位投递观察真实使用：不同岗位可能共享招聘入口、AI 对话和简历页面，但每个任务的进度不同。命名、分类、状态和备注均保持通用，避免过早把产品变成求职流程工具。

## 已知竞品类型

| 类型 | 需要进一步调查的使用方式 | 待验证的差异 |
| --- | --- | --- |
| Browser Tab Groups | 用分组和颜色管理相关网页 | 用户是否还需要跨关闭周期的任务备注与状态？ |
| Browser Profiles | 通过配置切换环境、账号和浏览记录 | 用户怎样区分账号隔离与任务组织？ |
| Workspaces | 将多个页面组织为工作区 | 用户实际使用哪些恢复和整理能力，痛点是什么？ |
| OneTab / Session Manager | 保存与恢复标签集合 | 显式的任务名称、进度能否带来额外价值？ |
| Notion / Excel / 飞书表格等任务记录工具 | 记录链接、任务与进度 | 浏览器内操作能否减少重复整理？用户是否愿意迁移？ |

这些是待研究的工具类型，不是最新功能或优劣评测。需要进一步验证差异，不直接下结论说本产品更好。

## 仍未验证的问题

- 用户自发形成的 Context 粒度是岗位、项目、阶段，还是某个晚上？
- 每次手动添加是否太麻烦？能否在不引入 AI 的前提下跑通闭环？
- 「保存后放心关闭」是否真能降低任务切换成本，而不只是增加收藏？
- 恢复只打开 URL，是否足够找回进度？备注是否被持续使用？
- 同一网页属于多个任务、跳转后脱离归属，用户是否理解并接受？
- 重启后不认领自动恢复标签，造成重复标签的频率和影响有多大？
- 页面中未保存的输入和动态登录状态是否阻碍用户使用关闭操作？
- 当前的分类和状态是否有价值，还是徒增填写负担？

## 用户研究待办

1. 找 3–5 位最近确实有多任务浏览需求的人，以秋招为首个场景，补充创作或学习观察。
2. 先观察他们用现有工具完成任务、收起和找回页面的过程，不先介绍「Context」术语。
3. 让参与者自行命名 2–3 个任务，保存相关网页；记录添加、关闭、恢复时的理解和疑问。
4. 隔一天请参与者恢复同一任务，观察是否找到入口、是否需要读备注、哪些页面多余或缺失。
5. 以手工访谈记录为主；0.2 另加了一个本地的临时研究脚手架（见 `DECISIONS.md` D4），只记录基础操作事件，不上传、不记录网址与标题，导出需用户确认，研究结束后整体移除。时间、错误和使用意愿都需要征求同意后记录。
6. 与参与者已有的分组、工作区或表格流程对照，记录保留旧工具的原因。
7. 特别演示同域名不同页面、共享标签、跳转、浏览器重启；观察保守关闭策略是否容易理解。

## 下一轮最值得讨论的五个问题

1. **Context 应该有多细？** 一个岗位、一次投递，还是整个秋招？让真实用户的命名来决定。
2. **何时用户会愿意保存并关闭？** 保存动作要嵌入什么任务节点，才能形成第二天继续使用的习惯？
3. **恢复到什么程度才算找回现场？** URL 加手写备注是否足够；哪些状态丢失最影响继续工作？
4. **标签的归属规则应该怎样表达？** 如何理解共享标签、页面跳转以及重启后的关联失效？
5. **相对现有工具的差异究竟是什么？** 用户愿意为哪些真实收益改变习惯，哪些需求其实已被 Tab Groups / Workspaces / 表格满足？

本轮到 MVP 骨架为止。以上均为后续讨论与研究问题，不构成第二阶段开发任务。
